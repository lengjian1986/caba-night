# CABAKURA LikeAdmin 后台实施方案

## 1. 技术选型

基于当前已部署的 `backend/likeadmin_php` 实施，不另起后台框架。

| 层级 | 方案 |
|---|---|
| 后台前端 | LikeAdmin Admin，Vue 3 + Vite + TypeScript + Element Plus + Pinia |
| 后端 API | LikeAdmin Server，ThinkPHP 8，多应用结构 |
| 数据库 | MySQL，使用 LikeAdmin 现有迁移/安装数据结构作为基础 |
| 缓存 | Redis，用于验证码、登录态、短期锁、异步任务状态 |
| 文件 | 先复用 LikeAdmin 文件/素材管理，后续可切 OSS/COS/Qiniu |
| 权限 | 复用 LikeAdmin 管理员、角色、菜单、按钮权限 |
| 部署 | Docker Compose，继续使用当前本地 Docker 环境 |

## 2. 总体架构

后台分三层推进：

1. 管理后台 UI：负责列表、表单、详情、审核、状态操作、导出。
2. Admin API：负责后台管理接口、权限校验、数据范围控制、审计日志。
3. App API：为前台 App 提供店铺、Cast、预约、取消、客服、认证等接口。

## 3. 复用 LikeAdmin 能力

优先复用现有组件和机制，减少自造基础设施。

| 能力 | 使用方式 |
|---|---|
| 菜单/权限 | 系统管理里的菜单、角色、管理员、按钮权限 |
| 表格分页 | 复用现有列表请求、`pagination` 组件 |
| 弹窗表单 | 复用 `popup`、`footer-btns` |
| 上传 | 复用 `upload`、`material/picker`、文件管理 |
| 富文本 | FAQ、协议、店铺介绍使用 `editor` |
| 字典 | 区域、标签、状态、取消理由等走字典/配置 |
| 导出 | 复用 `export-data`，订单/支付/退款/收据重点支持 |
| 权限按钮 | 复用 `v-perms` 指令控制审核、退款、导出等按钮 |
| 工作台图表 | 复用 ECharts |

明确不使用 LikeAdmin 自带的页面创建/代码生成方式。它生成的是表字段映射型页面和通用增删改查接口，无法表达本项目里的审核、状态流转、退款、订单确认、客服对话等业务动作。

本项目采用手写业务后台：

- 页面手写：按实际业务流程设计列表、详情、抽屉、弹窗、审核面板、状态时间线。
- 接口手写：按业务动作设计接口，例如店铺审核通过、订单确认、取消试算、退款处理。
- 服务手写：金额计算、状态机、权限范围、审计日志放到业务 Service/Logic，不放在页面里拼。
- 表结构手写：数据库服务业务模型，不用数据库字段直接反推页面。

## 5. 核心功能方案

### 5.1 工作台

展示后台待办和关键指标：

- 今日预约、待确认预约、待退款、待审核店铺、待审核身份、待处理工单。
- GMV、支付金额、退款金额、优惠券使用数。
- 热门店铺、热门 Cast、订单状态分布。
- 快捷操作入口。

### 5.2 会员管理

功能：

- 会员列表：手机号、昵称、会员ID、等级、认证状态、状态、注册时间。
- 会员详情：基础资料、预约记录、收藏、评价、优惠券、余额、通知设置。
- 会员状态：正常、禁用、注销申请中、已注销。
- 敏感信息脱敏：手机号、证件、卡号默认脱敏。

首期不做复杂 CRM，只做可查、可禁用、可追踪。

### 5.3 身份认证审核

功能：

- 电话认证记录。
- 证件正反面上传记录。
- 审核操作：通过、驳回、要求重传。
- 审核日志：审核人、审核时间、审核意见。

状态：

`not_started`、`phone_verified`、`document_pending`、`reviewing`、`approved`、`rejected`。

### 5.4 店铺管理与审核

店铺是后台第一核心对象，需要做资料审核和营业执照。

功能：

- 店铺资料维护：店名、假名、区域、地址、车站、营业时间、价格区间、标签、介绍。
- 营业执照上传：文件、许可编号、法人/经营主体、有效期、上传时间。
- 店铺审核：新增、执照变更、关键资料变更后进入审核。
- 审核动作：通过、驳回、要求补充资料、暂停展示。
- 前台展示控制：只有 `approved` 且上架的店铺允许在 App 展示和预约。
- 店铺管理员数据范围：只看所属店铺。

状态：

`draft`、`submitted`、`reviewing`、`approved`、`rejected`、`supplement_required`、`suspended`。

### 5.5 套餐管理

功能：

- 套餐名、价格、原价、折扣、时长、人数范围、预约截止时间。
- 是否含税、是否含服务费、是否饮放题、是否初回限定。
- 上架/下架/售罄。
- 按店铺隔离数据。

### 5.6 Cast 管理

功能：

- Cast 基础资料、所属店铺、标签、照片、排序、是否新人、是否推荐。
- 出勤排班：日期、开始/结束时间、是否可预约、最短预约时间。
- Cast 审核：资料变更可走审核，避免前台展示违规内容。
- 收藏数、评分、评价数只读统计。

### 5.7 预约订单

订单是业务闭环核心。

功能：

- 订单列表：订单号、会员、店铺、套餐、Cast、来店时间、人数、金额、订单状态、支付状态。
- 订单详情：订单快照、费用明细、优惠券、支付记录、退款记录、状态时间线。
- 店铺确认：确认预约、拒绝预约。
- 核销：二维码核销状态，记录核销人和核销时间。
- 备注：平台备注、店铺备注、客服备注。

状态：

`requesting`、`confirmed`、`unpaid`、`paid`、`visited`、`completed`、`cancel_requested`、`cancelled`、`refund_pending`、`refunded`、`refund_failed`。

### 5.8 取消与退款

功能：

- 取消理由字典。
- 取消申请列表：订单、用户、理由、详情、申请时间。
- 退款试算：支付金额、取消费、返金予定額、返金先。
- 退款处理：待处理、处理中、成功、失败、人工审核。
- 高风险操作审计：退款金额、操作人、操作时间、原因。

首期建议先做“后台人工确认退款状态”，等支付渠道确定后再接自动退款。

### 5.9 支付与财务

功能：

- 支付记录：支付渠道、流水号、金额、状态、回调日志。
- 退款记录：退款金额、退款渠道、状态、失败原因。
- 收据管理：申请、确认、生成 PDF、下载、作废。
- 导出：支付、退款、订单、收据。

卡片信息只保存支付 token 和脱敏展示字段，不保存完整卡号/CVC。

### 5.10 优惠券

功能：

- 优惠券维护：名称、类型、折扣/金额、有效期、总量、状态。
- 适用范围：店铺、区域、Cast、套餐、会员等级。
- 发放：手动发放、按等级发放。
- 使用记录：订单、用户、抵扣金额。

### 5.11 评价审核

功能：

- 店铺评价、Cast 评价分开管理。
- 审核通过后前台展示。
- 驳回需原因。
- 支持隐藏、置顶、举报处理。
- 标签字典独立维护。

### 5.12 客服中心

功能：

- FAQ 分类与内容管理。
- FAQ 热门、排序、浏览量。
- 客服工单：订单关联、分类、状态、处理人。
- 消息记录：用户消息、客服回复、系统消息。
- 客服配置：服务时间、自动提示文案。

首期可不做实时聊天，先做工单消息列表和刷新。

### 5.13 通知管理

功能：

- 通知模板：预约确认、来店提醒、取消退款、Cast 出勤、优惠券。
- 通知记录：发送对象、渠道、状态、阅读状态。
- 用户通知设置：按类型开关。
- 群发通知放 P1/P2。

## 7. 开发顺序

### 阶段一：后台基础和主数据

1. 新建 `cabakura` 业务目录、枚举、公共服务。
2. 建菜单和权限。
3. 建区域、标签、字典。
4. 做会员、店铺、营业执照、店铺审核。
5. 做套餐、Cast、排班。

### 阶段二：订单闭环

1. 订单列表和详情。
2. 订单状态流转。
3. 预约确认/拒绝。
4. 取消申请。
5. 退款记录和人工处理。
6. 支付记录只读查询。

### 阶段三：运营功能

1. 优惠券。
2. 评价审核。
3. 收据。
4. FAQ 和客服工单。
5. 通知模板和通知记录。

### 阶段四：优化

1. 工作台统计。
2. 导出和报表。
3. 首页推荐和搜索权重。
4. 店铺管理员数据范围加强。
5. 接真实支付、短信、对象存储、eKYC。

## 8. 实施原则

- 不使用 LikeAdmin 自带页面创建/代码生成器，不使用数据库映射型通用接口承载业务。
- 所有后台页面和接口按业务场景手写，列表查询、详情聚合、审核动作、状态流转分开设计。
- 所有核心业务状态使用枚举类，不在页面里写散字符串。
- 所有金额用整数分/日元最小单位存储，展示时格式化。
- 所有后台审核、退款、订单状态变更写入 `operation_audit_log`。
- 文件只保存文件 ID/路径/脱敏元数据，访问走鉴权接口。
- 店铺管理员的数据范围从查询层统一控制，不只在前端隐藏。
- P0 阶段不做复杂自动化支付退款，先保证后台人工闭环可用。

为了尽快把后台跑出业务形态，第一批只做这些：
